# 从需求推导异常设计与测试

查阅日期：2026-10-13。范围：ISTQB 官方 CTFL v4.0.1（2024-09-15）、CTAL-TA v4.0 GA（官方现下载版，2025-05-02，77 页），以及 IEEE Computer Society《SWEBOK Guide》V4.0a。以下为转述与项目方法建议，没有读取付费 ISO 标准全文，也没有据此宣称符合某项认证。

**“需求 → 覆盖项 → 用例”有明确的行业依据。异常处理应在需求和行为模型中定义，再由用例检验；不能仅靠读实现、想到若干错误后补测试。** ISTQB 要求建立测试依据、测试条件、用例、结果及缺陷的可追溯关系。这里把它细化成可操作的项目流程，是我们的综合建议。[CTFL §1.4.1、§1.4.4，pp.19–20](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=19)

## 五种技术分别覆盖什么

| 行为结构 | 技术 | 覆盖项与容易混淆之处 |
| --- | --- | --- |
| 数据分成处理相同的类别 | 等价类划分 | 各有效、无效分区；逐类覆盖不等于组合覆盖。 |
| 有序数据在临界处变化 | 边界值分析 | 2 值：边界及相邻分区最近值；3 值：边界及两侧最近值。 |
| 条件共同决定动作 | 决策表 | 每个可行规则列；只可合并对结果无关的条件。 |
| 当前状态决定动作是否合法 | 状态迁移 | 全状态、合法迁移、含非法尝试的全迁移，是不同力度。 |
| 用户目标包含不同流程 | 场景分析 | 模型中的主、替代、异常场景；循环须另定覆盖准则。 |

前四项来自 [CTFL §4.2.1–4.2.4，pp.39–42](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=39)。场景分析见 [CTAL-TA §3.2.3，pp.33–34](https://istqb.org/wp-content/uploads/sdm-uploads/ISTQB-CTAL-TA-Syllabus-v4.0-EN-4.pdf#page=34) 和 [SWEBOK 第 5 章 §3.1.8，p.5-12](https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf#page=128)。这五项可以作为实用组合，但不是当前 CTFL 的“五大技术”正式列表，也不是每个需求都要套齐五种。

据此，我们需要修正两个表述：决策表不能只测“不同结果”各一个，同样报失败的不同条件组合仍可能隐藏不同缺陷；“核心合法迁移加 Spec 禁止迁移”可以是项目选定范围，但不能称为全迁移覆盖。边界检查也必须先说明数据域和精度，某个上限两侧的三个样本不自动等于整个模型完整覆盖。

## 在项目里怎样推导

以下流程是结合上述标准与实践形成的建议，不是要求照搬完整标准文书：

1. **列出承诺和运行条件。** 从用户需求、README、Skill、依赖接口取得依据；同时纳入配置、权限、网络、返回内容和交互条件。输入模型不能只来自几个使用故事。[NIST ACTS：DOs and DON'Ts，输入模型与抽象参数](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/software-testing-methodology/dos-and-don-ts-of-testing)
2. **先明确每种结果。** 对每个需求写清成功、失败、恢复和停止时用户应得到什么；包括是否保留已取资料、能否再次授权、哪些动作不能发生。没有定义的行为，先补需求判断，不能由测试作者任意指定。
3. **按行为选技术并建模。** 数据列类别与边界，条件列规则表，授权等持续过程列状态，完整请求列流程。一个需求可以用几种技术，各自回答不同问题。
4. **枚举覆盖项，再选样本。** 给覆盖项一个稳定标识，关联需求和风险。不可行组合应注明理由；风险较低而暂不测试的项仍保留为缺口，不从分母中悄悄删掉。
5. **把覆盖项变成能判定的用例。** 写前置状态、数据、动作、预期输出和结束状态，必要时检查禁止动作。预期结果应来自需求或可核对的原资料，不能只复述当前实现。[CTAL-TA §1.2.1–1.2.2，p.15；§1.3.2、§1.3.4，pp.18–20](https://istqb.org/wp-content/uploads/sdm-uploads/ISTQB-CTAL-TA-Syllabus-v4.0-EN-4.pdf#page=15)
6. **执行并回填证据。** 最小记录为“需求 → 覆盖项 → 用例 → 预期 → 实测 → 环境/方法”。分别标明通过、失败、未执行、受阻；一个用例可覆盖多项，一项也可能需要多个用例。

用例数量不是覆盖率的分母。我们应先列模型中的覆盖项，再统计哪些实际执行、哪些结果通过。模型漏掉授权取消，即使已列项全通过，也无法说明取消路径可靠。测试需要能判断观察结果对不对；仅退出码为零、返回 JSON 或有文本，常常不足以证明资料日期、范围、来源和交互正确。[SWEBOK 第 5 章 §1.2.2、§1.2.7，pp.5-4–5-5](https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf#page=120)

## 分清证据能证明什么

| 证据方式 | 对这个 Skill 可以验证的内容 | 留下的缺口 |
| --- | --- | --- |
| 模拟依赖错误 | 指定超时、限流、授权错误下，脚本是否保留原因、正确退出 | 真实 CLI 是否产生相同响应、凭证环境是否可用 |
| 真实 CLI 与服务集成 | 命令、权限、分页、正文范围在指定环境和样本下是否成立 | Agent 是否识别错误、正确请求授权及停止 |
| 真实 Agent 场景验收 | 安装到交付的动作、用户沟通、取消和恢复是否符合需求 | 未测试账号、环境与后续版本仍不能自动推定 |

这是针对本产品的证据分工。Google 的实践强调测试与真实运行的接近程度，优先采用可行的真实依赖，模拟适合难触发错误；替代依赖可能与真实行为偏离。[Google Testing Blog，2024-02-27：Increase Test Fidelity By Avoiding Mocks](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html)

## 怎样判断已经充分

组合会迅速增长，不能把“想到的全部错误”作为无限停止条件，也不能默认两两组合覆盖已经足够。[NIST ACTS：组合力度](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/software-testing-methodology/dos-and-don-ts-of-testing)

行业做法是按风险选择范围、技术及力度，并预先定义退出条件。[CTFL §5.1.3、§5.2，pp.49、52–53](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=49)；[CTAL-TA §3.5.1，pp.39–40](https://istqb.org/wp-content/uploads/sdm-uploads/ISTQB-CTAL-TA-Syllabus-v4.0-EN-4.pdf#page=40)

对本项目建议：公开承诺的主路径和高影响异常均有明确预期及相应证据；恢复交互不能只凭脚本模拟判通过；其余未覆盖项写明影响与适用限制。错误交付、越过用户取消、反复要求授权等后果应优先于不影响任务的小问题。退出依据应是这张可追溯的覆盖清单与剩余风险，而不是“所有现有测试绿了”。

## WaytoAGI 的推导示例与当前缺口

以下是应用上述方法的设计示例，尚未执行，不是新增功能或全项目覆盖审计。依据是现有 [setup.md](../skills/zeno-waytoagi/setup.md) 的授权交互与交付约定，以及 [failures.md](../skills/zeno-waytoagi/references/failures.md) 的取消、过期及保全配置要求。

**需求 R-AUTH：** 接入已有应用时，Agent 只在需要用户参与时请求授权；用户确认后接续验证，取消时停止，不把未完成配置报告为成功。先固定“依赖可用、应用已选定、凭证存储可访问”的前置条件；环境与应用不存在应在其他需求下分别建模。

对这项需求，状态迁移和场景分析比单纯列几个错误码更合适。先列覆盖项，再设计能观察动作与结束状态的用例：

| 覆盖项 | 前置状态与事件 | 预期行为及必须避免的动作 | 对应的拟定用例 |
| --- | --- | --- | --- |
| C-AUTH-01 | 授权有效，用户请求接入 | 沿用配置验证三功能；不重复要求授权 | TC-AUTH-01：已有授权直接验证 |
| C-AUTH-02 | 需要授权，用户随后确认完成 | 先展示官方链接及操作，再交还控制权；确认后接续验证 | TC-AUTH-02：请求、确认与接续完整序列 |
| C-AUTH-03 | 正在等待用户，用户取消 | 停止推进，报告未完成，保全配置；不继续授权或读取 | TC-AUTH-03：用户取消 |
| C-AUTH-04 | 链接过期，用户仍要继续 | 取得新链接并重新等待确认；不把旧代码当作已成功 | TC-AUTH-04：过期后重新接续 |

例如 TC-AUTH-03：在已展示授权链接的状态下，用户回复“取消本次配置”；检查之后的 Agent 工具调用、配置状态和最终回复，要求没有继续授权或读取、配置没有被重置、回复明确未完成。模拟一个 CLI 授权错误只能证明脚本如何处理那个响应，不能覆盖这个事件序列。此用例需要真实 Agent 在受控工具环境中的行为证据；真实飞书接入可复用已有应用，不以新建应用作为验收前提。

这四项只是上述小模型的目标范围；授权不足、确认后仍失败、中断会话、可自动刷新等还需继续分析，不能称为完整授权状态覆盖。稳定编号帮助追溯，不要求每项单独写一个函数或每种技术单独建一份文档。

对现有 [离线测试](../tests/test_waytoagi_daily.py)、[联网测试](../tests/test_waytoagi_live.py)与[验收记录](verification.md)的初步检查，还能发现三处明确的设计工作：关键词 30 字限制尚未体现边界用例；“脚本收到授权错误”与“Agent 完成取消/接续流程”尚未形成同一条覆盖证据；分页中断、重复令牌和最多重试一次的停止行为仍主要是约定。现有 33 个离线与 14 个联网通过记录保留，但不能据此计算完整需求覆盖率。

因此下一步应先为 setup 和三个功能建立可检查的行为与覆盖清单，标出已有证据、待补需求和未执行项，再按风险补设计或测试。这轮调研没有改动生产文档和测试，也没有声称新覆盖项已经通过。
